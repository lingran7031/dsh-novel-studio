# 半成品分析归档协议

> 旧导入兼容：新的半成品导入、剧情改写统一优先使用 `novel-rewrite`，将原稿和分析保存到独立批次。只有用户明确恢复已有 `story/import/manifest.json` 的旧任务时才使用本协议，避免单一旧导入目录覆盖新版批次或正式资料。

本协议把一本写到一半的小说变成"可续写的资料库"：先切块，再并行抽取事实，再分域合并，最后裁定冲突、产出续写方案。全文永远不整体进入任何角色的上下文，所有中间产物落盘。

## 一、适用场景与前提

触发条件：用户提供半成品（`.txt` / `.md` 文件或直接粘贴），要求分析、归档、续写。

开工前必须确认：

1. 当前目录是不是标准项目：`novel_project(action="detect")`；不是则先与用户确认根目录，再 `novel_project(action="init")`；`prepare` 要求当前目录已是小说项目，否则直接报错。
2. 当前项目是否已有正文（`chapters/` 非空）：有则先问用户是"合并到现有项目"还是"新建目录导入"，避免覆盖已有章节与资料。
3. 文件在哪：首选让用户把文件放进小说目录，如 `source/原名.txt`，然后传相对路径；≤5 万字的短篇/片段可用 `text` 直接粘贴。
4. 编码：工具按 UTF-8（含 BOM）优先、必要时回退 GB18030（兼容 GBK）读取；仍失败则请用户转存 UTF-8。`.docx` 需先转 txt（让用户另存，或用当前环境可用的文档转换能力），本协议只处理纯文本。
5. 版权与授权：只处理用户有权使用的文本；分析结果仅存本地项目目录。

**交接关系**：Map 阶段每个分析者向 Lead 交接块笔记；Reduce 阶段架构师/作者/编辑分别向 Lead 交接自己的域；裁定与续写方案由 Lead 汇总后向用户汇报。任何一次交接回复都不超过 300 字，产物只落盘。

**写文件范围**：分析者只写 `story/import/notes/`；架构师写资料类文件与 `story/continuation-plan.md`；作者写 `story/style.md` 与 `story/summaries/`；编辑写 `story/import/conflicts.md`；裁定者写 `story/decisions/` 与 `meta/compass.json`；Lead 汇总更新 `story/import/report.md`（`prepare` 生成模板）、`chapters/`、`meta/progress.json`、`story/state.json`。`story/import/source.txt`、`manifest.json`、`chunks/` 由工具生成，任何角色不得手改。

## 二、阶段 0：评估规模与选择深度（强制用户确认）

调 `novel_import(action="prepare", path="<绝对路径>", source="source/原名.txt", maxChars=12000)`。

`prepare` 会切章、超长章节按段落切块，写入 `story/import/source.txt`、`story/import/chunks/0001.md` 等块文件与 `story/import/manifest.json`（每块含 `index`、`title`、`chars`、`file`），并在 `report.md` 不存在时生成分析报告模板；返回紧凑清单（章节数、块数、每块字数与路径），**不返回全文**。重复 `prepare` 会清理过期块，但不会清理旧笔记。

拿到清单后：估算 token（每个 1.2 万字块约 8k 输入 + 1.5k 输出），把"章节数、总字数、切块数、三档方案与预计成本"报给用户，用 `ask_user_question` 让用户选档。未确认档位不得开始 Map。

| 档位 | 做法 | 适用 |
|---|---|---|
| 快速 | 只精读最近 30 章，其余按目录/首尾段做摘要级扫描 | 百万字以上，想尽快续写 |
| 标准（默认） | 全书逐章摘要 + 人物/规则/时间线/伏笔抽取，最近 20 章细读 | 大多数情况 |
| 深度 | 全书逐章细读 + 双遍交叉校验 | 100 章以内，追求零设定冲突 |

选档后调 `novel_chapter(action="checkpoint", stage="importing", note="半成品导入：<来源>，<章节数>章 <块数>块")` 记录阶段，并把决定与成本写进任务板；后续若用户追加预算，再升级档位。

## 三、阶段 1：Map——并行抽取笔记

### 3.1 任务拆分

按 `manifest.json` 的 chunk 清单给每个块建一个分析任务（`team_task_create`，`write_scopes` 指 `story/import/notes/`）。每块一个分析者：

- 若当前模式提供 `subagent` 工具：每个 chunk 起一个分析子代理，同时在飞不超过 6 个，其余排队；
- 若没有 `subagent`：Lead 串行分批（每批 1–3 块）自行或派给当前空闲队友执行，笔记格式与验收标准不变，并在任务板注明"降级为串行"的原因。

### 3.2 分析者的硬性规则

1. 只读自己的 chunk 文件（必要时读同章相邻块），不读全书；chunk 开头一行 `<!-- chunk ... -->` 是元数据注释，分析时忽略。
2. 只记录原文写明的事实，**禁止补写、推断、圆场**；无法确定的写进"存疑"栏，标注"原文未写明"。
3. 每条事实带出处：`[chunk NNNN]` 或 `[第 X 章 · 原文首句……]`。
4. 笔记写入 `story/import/notes/NNNN.md`（编号与 chunk 对齐），目标 500–800 字，信息密度优先。
5. 向 Lead 交接：回复 ≤300 字，写块编号、覆盖章节、笔记路径、发现的重大矛盾数量；不贴笔记内容。

### 3.3 笔记模板（story/import/notes/NNNN.md）

```markdown
# Chunk NNNN 分析笔记
- 覆盖：第 X–Y 章（或某章片段）
- 字数：（本块字数）

## 出场人物与状态
- 姓名：身份/状态/本章目标/变化；出处

## 世界规则
- 规则：能约束什么；出处

## 时间线事件
- 时间 / 事件 / 参与者；出处

## 伏笔与未解线
- 线索：埋设位置、当前状态（未解/推进/已回收）；出处

## 关键情节
- 事件→后果；出处

## 文风样本
- 摘 2–3 句代表性原文（短句即可），标注叙述视角与语言特征

## 疑似矛盾与存疑
- 矛盾：两种说法各自出处；或"原文未写明：X"
```

### 3.4 Map 的断点与验收

- 断点：`story/import/notes/` 中已有非空笔记即视为该块完成；`novel_import(action="status")` 只返回 manifest 摘要（来源、编码、块数、章节数、总字数、创建时间），笔记完成度用 `glob`/`read` 检查 `story/import/notes/`，续跑只补缺块。
- 验收：每个 chunk 都有笔记；每条事实有出处；无凭空补写；重大矛盾已进"疑似矛盾"栏。不合格退回重做该块，不进入 Reduce。

## 四、阶段 2：Reduce——分域合并

Map 完成后按域拆分，并行执行：

### 4.1 架构师：合并资料库

读全部 notes，去重合并，产出：`premise.md`（沿革版）、`characters.json`、`world_rules.json`、`timeline.jsonl`、`foreshadow_ledger.json`、`relationship_state.json`、`outline.json` 或 `layered_outline.json`（已写章节的实况 + 下一卷草案）。要求：

- 每条资料尽量保留章号出处；
- 同一事实多笔记重复时取信息最全的一条；
- 笔记之间冲突的，不自行取舍，登记为待裁定条目交裁定者；
- 人物 `status` 以最后一章的状态为准。

### 4.2 作者：文风卡与历史摘要（仅导入阶段）

读 notes 中的文风样本与代表性章节，生成 `story/style.md` 文风卡（七项：视角、时态、语言风格、句子节奏、对话风格、意象/母题、禁忌），并为已分析章节生成 `story/summaries/NNN.md` 历史摘要（每章 ≤200 字，格式同单章摘要）。此阶段摘要用于补齐上下文，**不写新正文**。

### 4.3 编辑：冲突扫描

拿资料库回查原文（按 notes 引用的出处定向读 chunk），写 `story/import/conflicts.md`。格式：

```markdown
# 半成品冲突清单

| 编号 | 类型 | 冲突点 | 证据 A | 证据 B | 影响 | 建议等级 |
|---|---|---|---|---|---|---|
| C-01 | 人物 | 主角年龄前后不一 | 第 3 章：29 岁 | 第 28 章：34 岁 | 关系线、时间线 | 阻断 |

## 缺失与不确定
- <原文未交代但续写必须定的事实，如父母姓名、城市名>
```

类型用：人物、时间线、世界规则、伏笔、关系、设定缺失。阻断级冲突必须交裁定；缺失项列成"待用户确认问题"。

### 4.4 Lead：汇总与体检

汇总各域产物，跑 `novel_validate`：errors 清零（资料修复交架构师），warnings 逐条记录。把当前进度、资料库规模、冲突数、待确认问题补充进 `story/import/report.md`（`prepare` 已生成模板，直接填写/覆盖各节），并在任务板更新阶段。

## 五、阶段 3：裁定冲突

把 `conflicts.md` 中每条阻断/建议冲突连同证据派给裁定者。裁定者按 `novel-role-arbiter` 流程逐条裁：能靠原文判断的直接下结论并写 `story/decisions/NNNN-*.md`；不能判断的（如原文未写主角年龄）列成问题交 Lead 问用户，不猜。裁定后由架构师同步资料库，编辑复核冲突是否关闭。

## 六、阶段 4：续写方案与用户选向

架构师写 `story/continuation-plan.md`：

```markdown
# 续写方案
## 当前进度
- 已写至第 M 章，最后完整章：<标题>；主线状态、人物状态一句话
## 未回收线
- <按重要度排序，标伏笔编号与最近章号>
## 续写方向（三选一）
### 方向 A：<名称>
- 走向：<三句以内>
- 爽点/看点：
- 风险：
- 建议章数与节奏：
### 方向 B / C 同上
## 建议
- <推荐哪个方向，理由一句>
```

Lead 把三个方向整理成 ≤300 字的选择题，用 `ask_user_question` 让用户选。用户选定后：裁定者写路线决策（`story/decisions/`）并更新 `meta/compass.json`；架构师按方向补齐下一卷大纲；Lead 在 `report.md` 记录选择结果。

## 七、阶段 5：进入章节循环与续写起点

确定续写起点 N：最后完整章为 M，则从 M+1 开始；最后一章残缺时标记"中断半章"，由用户决定是接着写该半章还是从 M+1 开新章。

进入 `novel-chapter` 前补齐三件事：

1. 归位后 `meta/progress.json` 的 `completed_chapters` 会由 `materialize` 记为既有完整章节；`phase` 设为 `writing`，`current_volume` / `current_arc` 按续写方案；不归位时 `completed_chapters` 从新定稿章节开始记录；
2. `story/state.json` 用 `novel_chapter(action="checkpoint", stage="writing", note="半成品归档完成，从第 N 章续写")` 记录起点；
3. 归档完成后，建议把半成品里的完整章节按章归位到 `chapters/`：先经用户确认，再调 `novel_import(action="materialize")`（已有 `chapters/` 时加 `force=true`）；否则整本导出、上下文包的"上一章结尾"、进度校验都会缺前 M 章。最后一章残缺时只归位完整章节，残缺部分保留在 `story/import/`。第一篇续写的派单里，由 Lead 附上"上一章结尾"：从 `chapters/` 定稿取；若用户不愿归位，则从 `story/import/source.txt` 或末尾 chunk 摘最后 1500–2000 字并说明代价。从第二篇新章起，上一章就是本项目定稿，流程回归标准单章循环。

说明：半成品原文默认留在 `story/import/` 作为证据链。是否把历史章节归位进 `chapters/` 需用户确认（会改变"已定稿"口径）；`materialize` 会把 `completed_chapters` 置为已归位的完整章节。不归位时要在 `report.md` 记录该选择，并在开始时告诉用户"导出会缺历史章节"。

## 八、断点续跑

- 进度入口：`novel_import(action="status")` 看导入清单，`glob`/`read` 查 `story/import/notes/` 看笔记完成度；再读 `story/import/manifest.json`、`story/import/conflicts.md`、`story/decisions/`、任务板。
- 恢复顺序：Map 缺块→补笔记；Reduce 缺域→补该域文件；裁定未闭环→继续裁；方案未选→先问用户。
- **不要重新 `prepare`**：会重建 chunks 与 manifest，可能冲掉已有笔记映射；确需重切（如切章严重错误）必须先让用户确认，并先把 `story/import/notes/` 备份或迁移。
- 每个阶段完成即更新任务板与 `report.md`，不依赖聊天记录。

## 九、质量门槛（完成定义）

- [ ] `story/import/notes/` 中每个 chunk 都有非空笔记（用 `glob`/`read` 核对）；
- [ ] 每条资料条目尽量有出处，人物/规则/时间线/伏笔四类齐全；
- [ ] `novel_validate` errors 为 0，warnings 有处理记录；
- [ ] `story/import/conflicts.md` 每条冲突都有裁定记录或明确列为待用户确认；
- [ ] 历史摘要覆盖已分析章节，文风卡七项填满；
- [ ] `story/continuation-plan.md` 含三个方向与推荐理由；
- [ ] 用户已选定续写方向并记录在 `report.md` 与裁定记录中；
- [ ] `meta/compass.json` 已反映路线选择，续写起点已 checkpoint；
- [ ] 成本在实际确认的档位范围内，超出需提前报告用户。

## 十、成本控制

1. 全文只以 chunk 形式出现在分析者上下文，Lead 只看清单与笔记摘要。
2. 笔记目标 500–800 字，禁止把原文大段抄进笔记；文风样本最多三句。
3. Map 并行上限 6；Reduce 分域并行；不为省时间让单个代理读多块长文。
4. 汇报成本用"块数 × 单块估算"给区间，不用精确承诺；用户加预算才有权升级档位。

## 十一、汇报模板与交付格式（单条 ≤300 字）

**导入简报（≤300 字）**：识别章节/字数/块数、建议档位与预计成本、需要用户确认的一项（档位）。

**阶段简报（≤200 字）**：Map 完成 X/Y 块；Reduce 完成哪些域；冲突 N 条（阻断 X）；下一步。

**续写方案简报（≤300 字）**：已写至第 M 章、三条未回收主线、三个方向各一句、推荐方向与理由、请用户选择。

## 十二、失败与升级

| 情况 | 处理 |
|---|---|
| 切章明显错误（整本一块或切得过碎） | 停下，报告 Lead 与用户；确认后调整 `maxChars` 重跑 prepare，先保护已有笔记 |
| 文件找不到/编码错误 | 确认路径与编码；请用户转存 UTF-8；不猜内容 |
| 某块笔记反复为空或跑题 | 退回重做，缩小到该块单章；仍失败由 Lead 换分析者 |
| 笔记之间大量矛盾 | 正常现象，交 Reduce 与裁定，不在 Map 阶段强行统一 |
| 资料库合并后 validate 报错 | 架构师修；修不动则缩小合并范围，按章回滚 |
| 用户中途改档位/加书 | 重新评估成本与任务板，旧笔记不浪费，按新范围补缺 |
| 冲突无法判断且用户不答 | 列为待确认，不阻塞已能确定的续写方向；影响主线的必须等用户 |

## 十三、禁止事项

不把全文塞进任何单次上下文；不编造原文没有的事实；不跳过用户确认直接铺开全书分析；不在 Map 阶段改原文或删笔记；不擅自把半成品原文当成本项目定稿；不越过裁定者自行统一冲突设定。
